# NSFW Mask（加固版）

本地运行的图片内容审核与自动打码服务。基于上游
[`lmx566/NSFW-Guard-Pro`](https://github.com/lmx566/NSFW-Guard-Pro) 重写，
修复了其中的安全漏洞并收敛了不安全的默认配置。

**图片全程不出本机**，推理使用两个本地模型，不调用任何云端 API。

> 漏洞详情、修复方案与验证记录见 [SECURITY.md](SECURITY.md)。
> 如果你只想知道"上游有什么问题"，直接看那一份即可。

---

## 它做什么

```
浏览器上传 → FastAPI 接口鉴权 → 双模型本地推理 → 选择性打码 → 返回可下载的结果
```

- **NudeNet**（YOLOv8n / ONNX，模型已内置于 wheel，无需下载）
  逐部位给出坐标框。开启 Deep Scan 后会把图片切成 3×3 重叠瓦片再扫一遍，
  用于捕捉高分辨率图里的小面积目标。
- **Falconsai ViT 分类器** 对整图打分。当"干净"的置信度很高时，
  会放过露腹、紧身衣这类模糊区域，减少误杀。
- **三种打码**：高斯模糊 / 马赛克 / 纯色填充，强度可调。
- **三个接口**：文件上传、多文件批量、Base64 JSON。

## 快速开始

### 依赖要求

- Python **3.10+**（已在 3.13.12 上完整验证）
- 无需 GPU；有 NVIDIA 显卡可选装 CUDA 加速

### Windows 快捷启动

仓库根目录提供两个批处理脚本，装好之后可以直接双击：

| 脚本 | 作用 |
|---|---|
| `start.bat` | 预置 HuggingFace 镜像、打印 API Key、启动服务，**服务就绪后自动打开浏览器** |
| `run-tests.bat` | 依次跑完四个测试文件并汇总结果 |

`start.bat` 会自动在 `http://127.0.0.1:8000` 打开浏览器。它是**等到端口真正可连接之后**
才打开的（而不是固定 sleep 几秒），所以首次启动要加载模型也不会出现"无法访问此网站"。
不想让它自动开浏览器就 `set NSFW_NO_BROWSER=1` 再运行。

端口和监听地址都可以不改文件直接覆盖：

```bat
set NSFW_PORT=19000
set NSFW_HOST=0.0.0.0
start.bat
```

### 安装

```bash
# 1. 建虚拟环境
python -m venv venv
source venv/bin/activate        # Windows: .\venv\Scripts\Activate.ps1

# 2. 装依赖（CPU）
pip install -r requirements.txt
# GPU 用户改用： pip install -r requirements-gpu.txt

# 3. 启动
python -m uvicorn backend.app:app --host 127.0.0.1 --port 8000
```

首次启动会自动生成随机 API Key 并写入 `data/api_key`（权限 0600），
控制台会提示文件位置。读出它：

```bash
cat data/api_key          # Windows: type data\api_key
```

然后打开 <http://127.0.0.1:8000>，把密钥粘贴到右上角输入框。

**不想每次都填？** 勾上输入框旁边的「**记住**」即可 —— 密钥会保存在本机浏览器里，
以后打开自动填好。默认不勾选，此时密钥只存在会话存储中，关掉标签页就失效。
（服务只监听 `127.0.0.1`，所以持久化在本机风险有限；但如果你之后改成对外监听，
建议别勾。）

也可以一键安装：`install/install_linux.sh` 或 `install/install_windows.ps1`。
Linux 脚本会顺带写好 systemd 服务（含 `NoNewPrivileges`、`ProtectSystem`
等基础加固，密钥通过 0600 的 `EnvironmentFile` 注入）。

### Docker 之外的部署建议

默认只监听 `127.0.0.1`，这是有意为之。要对外提供服务：

```bash
NSFW_HOST=0.0.0.0 python -m uvicorn backend.app:app --port 8000
```

**务必在前面加一层反向代理**完成 TLS 与访问控制，不要把 8000 端口直接暴露到公网。

## 配置

全部通过环境变量控制，完整清单见 [`.env.example`](.env.example)。常改的几个：

| 变量 | 默认值 | 说明 |
|---|---|---|
| `NSFW_API_KEY` | 自动生成 | 少于 16 字符会拒绝启动 |
| `NSFW_HOST` | `127.0.0.1` | 改成 `0.0.0.0` 才对外可达 |
| `NSFW_PORT` | `8000` | |
| `NSFW_DATA_DIR` | `./data` | 密钥、上传件与中间产物的存放位置 |
| `NSFW_OUTPUT_DIR` | `./output` | **打码结果的存放位置**（见下） |
| `NSFW_MAX_CONCURRENCY` | `2` | 同时进行的重推理任务数 |
| `NSFW_MAX_BATCH_FILES` | `20` | 批量接口单次上限 |
| `NSFW_MAX_FILE_SIZE` | `10485760` | 单张上限，10 MB |
| `NSFW_RETENTION_SECONDS` | `3600` | 中间产物保留时长（不影响 output/） |
| `NSFW_DEEP_SCAN` | `1` | 关掉可明显提速 |
| `HF_ENDPOINT` | — | 国内网络设为 `https://hf-mirror.com` |

### 文件存放位置

| 目录 | 放什么 | 会被自动清理吗 |
|---|---|---|
| `output/` | **打码结果**，命名形如 `masked_20260923-201530_photo.jpg` | **不会**，留着给你取用 |
| `data/processed/` | 原图副本、自动遮罩位图（手动改遮罩要用） | 会，默认保留 1 小时 |
| `data/uploads/` | 上传时的临时副本 | 会 |
| `data/tmp/` | 临时文件 | 会 |

`output/` 不会被自动清理 —— 你要的就是把结果存这里，清了就毁掉这个用途了。
不想堆积就自己定期删，或者把 `NSFW_OUTPUT_DIR` 指到别处。

### 界面说明

- **语言**：右上角可切换 中文 / English / 日本語，即时生效并记住选择；
  检测明细里的部位名和原因会一并翻译。

- **一键填写**：点一下自动读入 `data/api_key` 的密钥。该端点只响应本机回环请求；
  服务一旦对外监听，必须在反向代理上封掉 `/api/local-key`。
- **上传图片**：单一入口，**智能识别** —— 点击是多选图片；把整个文件夹拖进
  上传区会递归处理其中全部图片，结果输出到 `output/<同名文件夹>/`。
  **文件夹名保留原名**（中文等 Unicode 字符直接使用），同时拖多个文件夹
  时各归各的目录。触发限流时自动退避重试。
- **手动调整遮罩**：通栏放在页面下方；笔刷是和大小一致的圆圈预览；
  支持**撤回/恢复**（Ctrl+Z / Ctrl+Y，最多 12 步）。
- **同名覆盖**：`output/` 里的结果名形如 `masked_照片.jpg`（不带时间戳），
  同一张图重复处理/重新涂抹会覆盖旧结果，不会堆积副本。

### 国内网络的注意事项

ViT 分类器的权重（约 340 MB）在首次运行时从 HuggingFace 下载。
直连通常失败，请先设置镜像：

```bash
export HF_ENDPOINT=https://hf-mirror.com
```

**下载不到也能用**：分类器加载失败时服务照常启动，自动退化为"仅 NudeNet 检测器"
模式，打码功能不受影响。健康检查接口的 `engines_loaded` 字段可以确认模型状态。
启动时会打印具体的失败原因和排查步骤，顺着提示做即可。

### 常见问题

**打码规则（pixiv / 严格）**

界面上可选两套预设，对应不同的平台审核口径：

| 预设 | 遮 | 不遮 |
|---|---|---|
| **pixiv 投稿规范**（默认） | 性器官与肛门（阴蒂、阴部、阴茎、肛门） | 臀部、胸部、睾丸、一线天、未掰开的肛门、腹部 |
| 严格（全部敏感部位） | 上述全部，外加裸露的胸部与臀部 | 腹部（被遮挡类仍按防误杀判定） |

**关于 pixiv 规则的固有限制，必须说清楚** —— 这是检测模型的粒度问题，不是配置问题：

1. **模型分不清"掰开"与"没掰开"。** NudeNet 只有 `EXPOSED` / `COVERED` 两档，
   "一线天"和"未掰开的肛门"在真实照片里经常仍被标成 `EXPOSED` 而被打码。
2. **没有独立的"睾丸"标签。** 男性生殖器的检测框通常把阴囊一起框进去，
   所以睾丸会跟着阴茎一起被遮，无法只遮阴茎。
3. 这两类误差只能在「手动调整遮罩」里修：擦掉不该遮的，补上该遮的。

**接触区域（交合、口交、生殖器贴近面部）**

这类姿势有一个共同难点：接触部位本身在模型里往往没有独立标签，两个框之间
的缝隙就是漏遮的位置。所以引擎在判定之后做了一步**几何关联**：

- **相邻合并**：两个必遮框重叠或间距小于短边 45% 时，并成同一遮罩区域，
  缝隙一起遮住（交合场景）。
- **面部延伸**：生殖器框与面部框相距不超过自身尺寸 1.6 倍时，把生殖器框
  延伸到面部边缘为止 —— 中间的接触带被遮住，面部内部不进入。

被合并/延伸的区域在「检测明细」里会写明原因（"相邻部位已合并"/"已向邻近面部延伸"）。
这类区域**强制用矩形完整覆盖** —— 轮廓分割会把缝隙裁掉，正好漏掉要遮的地方。

### GPU 加速

程序默认 `NSFW_DEVICE=auto`：检测到可用的 CUDA 就用 GPU，否则退回 CPU。

本机实测（RTX 5070 Ti，onnxruntime-gpu 1.30 + torch 2.14.0+cu130）：
检测器与 ViT 分类器都跑在 GPU 上，320 分辨率单图推理约 0.1s。

- 强制只用 GPU：`set NSFW_DEVICE=cuda`（环境不满足会启动失败并给出安装指引）
- 强制 CPU：`set NSFW_DEVICE=cpu`

安装 GPU 依赖（已装好可跳过）：

```bash
pip uninstall onnxruntime
pip install onnxruntime-gpu nvidia-cuda-runtime-cu13 nvidia-cudnn-cu13 nvidia-cublas-cu13
pip install torch==2.14.0+cu130 --index-url https://download.pytorch.org/whl/cu130
```

Windows 上 CUDA DLL 通常装不进系统 PATH —— 程序会自动把
`site-packages/nvidia/*/bin` 与 `torch/lib` 加进 DLL 搜索目录，
这也是 `CUDAExecutionProvider` 能否启用的关键。

### 轮廓贴合：SAM 分割（真正的「PS 快速选择」）

「遮罩形状 → 贴合部位轮廓」由 **SAM（Segment Anything）** 驱动：以检测框为提示，
分割出部位的真实边界，只对轮廓内打码。

为什么换掉 GrabCut：GrabCut 只认颜色分布，**部位与周围皮肤颜色相近时找不到
边界，只能把整个检测框判成前景** —— 表现就是"怎么调都还是矩形"。SAM 是用
上亿张图训练的分割模型，没有这个局限。实测同一个检测框：

| 模式 | 遮到周围皮肤的像素 |
|---|---|
| 矩形 | 4001 px |
| 轮廓贴合（SAM） | **0 px**（目标覆盖 98%） |

见仓库根的 `sam-comparison.png`。

- 模型约 358MB，存放在 `models/sam-vit-base/`；缺失时运行
  `python tools/fetch_sam.py` 下载（自动走 hf-mirror）。
- **没有模型也能跑**：SAM 不可用时自动退回 GrabCut，再退回矩形。
- 每张图一次前向处理全部检测框（GPU 上约 0.2s）；用 `NSFW_SAM=0` 可关闭。
- 合并/桥接区域（交合、口交的接触带）仍强制矩形 —— 缝隙正是要遮的部分。

### 女性阴部打码（含一线天）

NudeNet 对「掰开」和「一线天（未掰开）」输出同一个标签
`FEMALE_GENITALIA_EXPOSED`，模型层无法区分 —— 因此一线天也按同一
门槛打码（阈值 0.10 = 检测下限，即模型检出的都遮）。

| 部位 | 行为 |
|---|---|
| 女性阴部（含一线天） | **全部打码** |
| 男性生殖器 / 交合 | 原有逻辑不变 |

如果以后想恢复「一线天放行」，设 `NSFW_FG_THRESHOLD=0.45` 并配合
`NSFW_FG_MIN_MASK=0.15`（掩膜面积确认机制仍保留在代码里）。

- **画面里有多个同类部位**（如多个阴茎）：相邻的同类框不会合并成
  一大块 —— 每个都独立走轮廓贴合。合并只发生在异类之间（交合的
  接触带）。
- **男性生殖器也有专属门槛**：`NSFW_MG_THRESHOLD`（默认 0.10）。
  觉得误检多（把别的东西也遮了）就调高，比如 0.35；漏检多就保持
  0.10。女性阴部同理是 `NSFW_FG_THRESHOLD`。专属门槛比灵敏度门槛
  严时生效，否则灵敏度说了算。
- 掩膜同时做了精修：只保留检测框（+8px）内的最大连通域，
  SAM 掩膜溢出到衣服/腿上的部分会被裁掉。

### 遮罩内收（解决「矩形 + 遮到周围皮肤」）

NudeNet 的检测框普遍偏松，而轮廓分割在"部位与周围皮肤颜色相近"时找不到边界、
只能退回矩形 —— 两件事叠加就是你看到的"矩形框 + 糊到周围皮肤"。

**遮罩内收**（默认 15%）按检测框宽高的百分比从四周向里缩，直接裁掉松出来的那圈。
实测同一个检测框（部位本体只占 74%）：

| 内收 | 遮到皮肤的像素 |
|---|---|
| 0% | 4001 px |
| **15%（默认）** | **9 px** |
| 25% | 0 px（但部位边缘可能露出，别调太大） |

见仓库根的 `inset-comparison.png`。

### 检测召回：分辨率与分数下限

原库有两处写死的东西严重限制召回，现已可配置：

| 项 | 原库 | 现在 | 说明 |
|---|---|---|---|
| 推理分辨率 | 320px（写死） | `NSFW_DETECTOR_RESOLUTION`，默认 **320** | 320n 是按 320 训练的：提到 640 对远处小目标有利，但**特写大目标反而会漏**（实测回归），所以默认保持 320，小目标交给 Deep Scan 瓦片 |
| 分数下限 | 0.2 / 0.25（写死） | `NSFW_DETECTOR_SCORE_FLOOR`，默认 **0.10** | 原库在内部就把低置信检出丢掉，根本到不了灵敏度那一层 |

下限降低之后，最终遮不遮仍由「检测灵敏度」决定，所以误杀风险可控。
配合「高召回」档（0.20）可以吃到现在 0.20~0.25 之间原本被扔掉的检出。

> 调过分辨率/下限之后如果发现该遮的没遮，先把分辨率改回 320 再看 —— 两次实测回归都证明：640 输入会让 320 训练的模型漏掉特写大目标。

预处理与坐标还原搬运自 nudenet 3.4.2（MIT）的 `_read_image` / `_postprocess`，
除上述两处外逐行一致；顺带修了它只认 4 通道输入、内存图像必须落盘的问题。

**检出率不够？换大模型**

口交这类姿势 320n 小模型经常整个检不出来（上面两条几何规则只在"至少检出
生殖器"时才起作用）。这是模型召回上限，调参无效。换 640m 大模型能明显改善：

```bash
python tools/fetch_model.py        # 下载 640m（约 170 MB）到 models/
```

重启服务即自动启用，无需配置。网络受限时先设代理：
`set HTTPS_PROXY=http://127.0.0.1:7890`。
（注意：GitHub 的 release 资产在部分网络下会被重定向到登录页，脚本会检测并提示。）

**某些图没被识别到 / 该遮的没遮住？**

先看结果页的「检测明细」——它会列出模型检出的每一个部位，以及**没打码的具体原因**。
最常见的原因是「分数低于门槛」：模型确实检出了，但置信度不够高，被策略放过了。

这时候把 **检测灵敏度** 调高即可：

| 档位 | 一级部位门槛 | 说明 |
|---|---|---|
| 高召回 | 0.25 | 模型给出的任何疑似都遮。**男性生殖器建议用这档** |
| 标准（默认） | 0.30 | |
| 严格 | 0.60 | 少误杀，可能漏 |

`must` 级部位（当前规则要求必遮的那些）**不受"防误杀"逻辑影响** ——
只要分数过门槛就一定会遮。`ambiguous` 级（仅 strict 规则有：被衣物遮挡的版本、腹部）
会受整图判定影响，因为它们在正常照片里也经常出现。

**为什么男性生殖器特别容易漏？** 两个原因叠加：一是 NudeNet 的 320n 是小模型，
对这个标签给分普遍偏低；二是模型库内部写死了 `NMSBoxes(..., 0.25, ...)`，
**分数低于 0.25 的候选在依赖库内部就已经被丢掉了**，我们拿不到更低分的选项
（所以最宽松的档位也只能是 0.25）。如果这一档仍然漏，说明是模型本身的召回上限，
可以换用更大的 640m 模型：从 NudeNet 仓库下载 640m 的 onnx，然后设
`NSFW_DETECTOR_MODEL=<路径>` 指向它。

**打码范围太大，糊了一整片？**

三层控制，从粗到细。**如果自动的都不满意，直接用手动涂抹** —— 那是最终手段。

**第零层：手动涂抹（最可控）**

结果页有「手动调整遮罩」：原图上直接涂抹，**涂哪里就只打哪里**，完全不受模型判断影响。
涂完点「按此遮罩重新打码」即可。支持涂抹/擦除切换、笔刷大小、「恢复自动遮罩」和「全部清除」。

这一层之所以必要：自动分割靠颜色分布区分前景背景，而生殖器与周围皮肤
**颜色几乎完全相同**时，算法根本找不到边界，只能返回整个检测框。
这不是参数没调好，是方法的固有局限。想要精确，就得人来指定。

> 实现注意：原图预览走服务端签发的地址，**不要**用 `FileReader.readAsDataURL`
> 把文件转成 data URL —— 大图时那份数据（约 1.37 倍体积的字符串 + 解码位图）
> 会与编辑器自己的图片加载叠加，曾把渲染进程直接压崩，表现为编辑器一直
> 停在"正在载入原图…"。已用 800/1600/2400 三种尺寸回归验证。

**第一层：遮罩形状（默认「贴合部位轮廓」）**

以检测框为种子分割出部位的**真实边界**，只对轮廓内打码。
边界明显时效果很好（实测同一个框：矩形遮住 20581 px → 轮廓只遮 16535 px，**-20%**，
周围皮肤完全不动）。边界不明显时会自动退回矩形 —— 对打码工具来说，
多遮一点远比漏掉安全。仓库根的 `contour-comparison.png` 有对比图。

| 模式 | 行为 |
|---|---|
| 贴合部位轮廓 | 分割出轮廓，顺着边缘走（默认） |
| 矩形框 | 把整个检测框涂满（原行为） |

**第二层：遮罩扩张**

以检测框（矩形模式）或轮廓（贴合模式）为基准向外扩多少像素。
原版硬编码成高风险时 40px —— 一个 28×28 的检测框会被撑成 108×108，
面积放大 14 倍。现在默认只有 3px。

**第三层：边缘羽化**

轮廓边缘的过渡宽度，默认 2px。设成 0 就是硬边。

**参数**：`shape_mask` = `1`/`0`（或 `shape`/`rect`），`feather` = 0–30。

**设置会记住吗？**

会。所有参数（打码方式、强度、灵敏度、遮罩形状、扩张、羽化、颜色）都会自动保存，
下次打开自动恢复上次的取值。想回到初始值点「恢复默认设置」。
API Key 单独处理 —— 只有勾了「记住」才会持久化。

**页面能打开、样式也正常，但滑块拖不动、点上传没反应？**

这是最容易被忽略的一类故障。根因是**系统 MIME 表把 `.js` 判定成了 `text/plain`**：
Windows 上 `mimetypes` 会读取注册表里 `HKEY_CLASSES_ROOT\.js\Content Type` 的值，
只要机器上装过某个软件把它写成 `text/plain`（不少编辑器、打包工具会这么干），
`/js/app.js` 就会以 `text/plain` 返回。叠加我们设置的
`X-Content-Type-Options: nosniff` 之后，浏览器直接拒绝执行该脚本 ——
于是页面渲染正常（HTML/CSS 没受影响）、日志里静态文件全是 200，但**所有交互全部失效**。

程序启动时会自检并自动修正，同时打印一行提示：

```
[提示] 本机系统 MIME 表把 .js 判定为： text/plain
       已强制修正为 text/javascript。...
```

看到这行说明已经自动修好了，不需要你做任何事。它兜底的手段是在启动时对
`.js / .css / .html / .svg / .ico / .webp` 等扩展名做强制覆盖，不信任系统表。

想手动确认前端脚本有没有跑起来，打开浏览器控制台执行：

```js
document.documentElement.dataset.appReady   // 返回 "true" 即脚本已正常执行
```

**分类器报 `config.json is not a valid JSON file`，但网络明明没问题？**

这是**下载被中断后残留的损坏缓存**导致的。HuggingFace 会先写入 blob 再建快照链接，
中途失败会留下一个空文件，之后每次启动都读这个坏文件、报出与真实原因无关的 JSON 错误。
删掉对应的缓存目录再重启即可：

```bash
# 路径以启动日志里打印的那一行为准
rm -rf ~/.cache/huggingface/hub/models--Falconsai--nsfw_image_detection
# Windows: rd /s /q "%USERPROFILE%\.cache\huggingface\hub\models--Falconsai--nsfw_image_detection"
```

**端口 8000 被占用，或者不知道服务跑在哪个端口？**

`start.bat` 会自己解决这件事：它从 8000 开始往后找最多 20 个端口，
用第一个空闲的，并**在控制台明确打出实际使用的地址**（端口不是 8000 时会额外提示）。

```
[NOTICE] Port 8000 is already in use.
         Using port 8001 instead. (Set NSFW_PORT to change.)

  >>>  OPEN THIS IN YOUR BROWSER:   http://127.0.0.1:8001
```

想固定用某个端口，运行前设置即可：`set NSFW_PORT=9000`。

## 接口

鉴权：所有处理类接口都需要请求头 `X-API-KEY`。

| 方法 | 路径 | 说明 | 限流 |
|---|---|---|---|
| `POST` | `/api/process` | 上传单张图片 | 30/分钟 |
| `POST` | `/api/process-batch` | 多文件上传（用 `files` 字段传多个） | 5/分钟 |
| `POST` | `/api/process-base64` | JSON 传 Base64，可要求返回 Base64 | 30/分钟 |
| `POST` | `/api/remask` | 按手工遮罩重新打码（见下） | 30/分钟 |
| `GET` | `/api/files/{name}?t=<令牌>` | 取回结果图 / 原图 / 遮罩位图 | — |
| `GET` | `/api/health` | 健康检查 | — |
| `GET` | `/api/docs` | 自动生成的 OpenAPI 文档 | — |

参数：`mode` = `blur`/`pixel`/`solid`，`intensity` = 3–199，`color` = `#RRGGBB`，
`sensitivity` = `strict`/`balanced`/`aggressive`，`padding` = 0–60（像素），
`shape_mask` = `1`/`0`，`feather` = 0–30（像素）。

下载地址由服务端在响应中给出，形如
`/api/files/processed_<uuid>.jpg?t=<过期时间>.<HMAC 签名>`。
令牌与文件名绑定且有有效期，**不带令牌或换文件名访问一律 403**。

`/api/process` 的响应还会带两个地址，供手动改遮罩用：

| 字段 | 内容 |
|---|---|
| `original_url` | 原图（受同一套保留期清理） |
| `mask_url` | 自动遮罩的灰度位图，白色 = 已打码。可直接取回作为涂抹的起始状态 |
| `decisions` | 逐个检测框的处置结果：`label` / `score` / `censored` / `reason` / `shape` / `mask_ratio` |

`POST /api/remask` 用来按自己的选区重新打码，**只遮你指定的地方**：

```bash
curl -X POST http://127.0.0.1:8000/api/remask \
  -H "X-API-KEY: $KEY" -H "Content-Type: application/json" \
  -d "{\"id\":\"<process 返回的 id>\",\"mask\":\"data:image/png;base64,<白色为打码区>\",
       \"mode\":\"blur\",\"intensity\":51,\"feather\":2}"
```

遮罩尺寸与原图不一致时会自动对齐，空遮罩则原样返回。

```bash
# 单张处理
KEY=$(cat data/api_key)
curl -X POST http://127.0.0.1:8000/api/process \
  -H "X-API-KEY: $KEY" \
  -F "file=@photo.jpg" \
  -F "mode=blur" -F "intensity=51" -F "color=#000000"
```

## 测试

```bash
python tests/test_security.py        # 文件名白名单、令牌签名、密钥管理
python tests/test_engines.py         # 打码逻辑、阈值、并发、Deep Scan
python tests/test_pipeline_stub.py   # 分类器链路（用桩，不需联网）
python tests/test_api_e2e.py         # 起真实服务跑全流程 + 原漏洞回归
```

`test_api_e2e.py` 会自己拉起一个 uvicorn 子进程（端口 8123），跑完自动关掉，
无需手工准备环境。四项全部为零退出码即为通过 —— 当前实测 **336 条断言全部通过**。

> 若你的机器上设置了 `HTTP_PROXY` 之类的代理变量，测试脚本已用
> `trust_env=False` 绕过，避免本机请求被转发给代理导致误报。

另有一个**真实浏览器 UI 测试**（可选，需要 Node 18+ 与本机装有 Chrome/Edge）：

```bash
node tests/test_ui_browser.mjs
```

它会用 Chrome 无头模式打开页面，真的去拖滑块、真的通过文件选择框上传图片、
真的在画布上涂抹后重新打码，断言结果图渲染出来。后端接口全绿并不代表前端能用。
运行前请先让服务在 `127.0.0.1:8000` 上跑着。当前实测 **84 条断言全部通过**。

另外有一个**分割能力诊断工具**，用来量化"轮廓贴合在什么条件下有效"：

```bash
python tests/diagnose_segmentation.py
```

它构造两组对比场景（肤色差异明显 / 很弱），打印遮罩面积、目标覆盖率与
多遮的皮肤像素数。跑一下就能明白为什么自动分割在肤色相近时不可靠 ——
这不是参数问题，是方法的固有局限，所以界面上才提供手动涂抹。
